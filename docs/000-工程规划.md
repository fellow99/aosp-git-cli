## 1. 背景与定位

### 1.1 一句话定位

**以 AAR 形式发布的、Android 版 `git` 命令行可执行**——NDK 交叉编译的 `libgit_cli.so`
（arm64-v8a，exec 型 PIE），zlib/curl/OpenSSL 静态链入，assets 随包 git 模板与 CA bundle。

### 1.2 边界

| 在范围内 | 不在范围内 |
|---|---|
| 交叉编译、exec 门禁、AAR 打包、发布 | ssh 远程传输（需另带 openssh/dropbear，二期） |
| git 模板/CA 的随包与出处记录 | 子模块/大文件协议的特殊支持承诺 |
| 版本事实源 `git-cli.lock.json`（独立 semver） | git 钩子依赖的外部工具（perl/tcl 明确不编） |

## 2. 版本规则

制品版本 = git 上游版本，独立 semver；升级 = lock 增项 + CI 重建。

## 3. 技术方案

### 3.1 制品形态

```
git-cli-<ver>.aar
├── jni/arm64-v8a/libgit_cli.so    # exec 型 PIE（zlib/curl/openssl 静态，16KB 对齐）
└── assets/git-bridge-tools/…      # templates/ + cacert.pem（M1 投放）
```

- configure 缺项关闭：`NO_TCLTK` / `NO_GETTEXT` / `NO_ICONV` / `NO_REGEX`（不引入源码补丁）；
- 静态依赖链入 → DT_NEEDED 只剩系统库（白名单门禁天然满足）；
- 打包 `useLegacyPackaging=true`；命名 `libgit_cli.so`。

### 3.2 exec 型门禁 profile

与 node-cli/python-cli 同 profile（ET_DYN/INTERP=系统 linker64/白名单/16K/sha/size）。

### 3.3 构建链路（M1 实现）

fetch（git + zlib + curl + openssl 四个源码包，各带 sha256）→ build（configure NO_* +
静态链 + 16KB LDFLAG）→ provision（exec 门禁 + 投放）。

开放问题（M1 拍板）：四个静态依赖的版本钉选表（写入 lock.builtFrom.deps）；git 版本钉选
策略（固定 + 显式升级）；GPLv2 对应源码义务的 Release 归档形态。

### 4.1 发布模式（GitHub Release 先行、Maven Central 随后）

沿用 aosp-node-pty 的两段式发布：

1. **先行：GitHub Release（M1，tag `v<gitver>` 推送触发）**——归档
   `git-cli-v<ver>-android-arm64-v8a.tar.gz`（libgit_cli.so + templates/CA assets + 元数据 +
   LICENSES）与 `.sha256`，lock 回写；**归档必须同时分发构建所用源码 tarball 与构建脚本**
   （git 为 GPLv2，对应源码义务以此满足）；
2. **随后：Maven Central（M3）**——执行口径按工作区
   [`docs/发布到maven-central.md`](../../docs/发布到maven-central.md) runbook（§2 一次性凭据 →
   §4 发布前检查 → §5 上传 → §6 核验回填）；RELEASE=false 默认。

- 与 pty 的差异：版本源 `CLI_VERSION`（= git 上游版本，独立 semver，无配对顺序要求）；
  GPL 对应源码以 Release 归档链接为准（⬜ Maven 阶段 AAR/sources 的 GPL 措辞 M1 定稿）
  （runbook §10 已登记本线复用）。

## 5. 质量门禁汇总

exec profile 门禁（同 node-cli）+ 不入库 + 可复现 + 许可（**GPLv2 对应源码义务**）+
发布卫生（RELEASE=false 默认）。
