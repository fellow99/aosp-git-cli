## 1. 背景与定位

### 1.1 一句话定位

**以 AAR 形式发布的、Android 版 `git` 命令行**——NDK 交叉编译的 `libgit_cli.so`
（arm64-v8a，exec 型 PIE），zlib/libcurl/OpenSSL **静态链入**；**https 传输依赖独立的
remote helper 可执行**（以 `lib*.so` 随包 + `filesDir/gitexec` 符号链接农场，见 D5/§5.2），
assets 随包 git 模板、CA bundle 与农场清单。终端里由 node-pty 经 `forkpty` + `execve`
启动，提供真正的 `git` 命令（Termux 为完整先例）。

### 1.2 为什么需要它

- 原生 Android 没有 git（`/system/bin` 只有 mksh 与 toybox）；
- 终端（PTY）需要**独立进程**的真 `git` 命令；进程内 JS 替代（isomorphic-git）已被
  工作区 §3.3 否决（协议覆盖不全、无命令形态）；
- node/python 生态的前置能力：pnpm/npm/pip 与各类脚手架大量依赖 `git clone` 拉取。

### 1.3 边界（在范围 / 不在范围）

| 在范围内 | 不在范围内 |
|---|---|
| `libgit_cli.so` 与 **helper 全集**的交叉编译、exec 门禁、AAR 打包、发布 | ssh 远程传输（`git@…` / `ssh://` 需另带 openssh/dropbear，二期；工作区 §9.4 M4 再议） |
| helper 农场清单（gitexec-manifest）与门禁白名单设计（§5.2/§5.3/§6） | 仓库钩子（hooks）的运行期执行——filesDir 不可 exec，git 视为无钩子（§7.2；属消费方限制，非本仓能力） |
| git 模板/CA/农场清单的随包、物化与 sha256 出处记录 | perl/tcl 依赖的子命令（send-email/svn/gitk/git-gui/cvsserver，NO_PERL/NO_TCLTK 明确不编） |
| 版本事实源 `git-cli.lock.json`（独立 semver） | 子模块/大文件协议的特殊支持承诺；服务端角色（daemon/托管型 receive-pack） |

## 2. 版本规则

- 制品版本 = git 上游版本，**独立 semver**，与 node 系无配对（无 NODE_MODULE_VERSION 约束）；
- 升级 = lock 增项 + CI 重新构建（镜像 pty 的 release 纪律）；
- 当前 draft 计划版本 **`2.51.0`**（坐标 `io.github.fellow99:git-cli:2.51.0`）：M1 开工时
  以 CI 实际可构建的最新稳定版钉选并回写（README 同口径）；
- **四源各自独立钉版 + sha256**（git / zlib / curl / openssl，另加 cacert.pem 输入），
  不随上游浮动，版本表进 `lock.builtFrom.deps`（§4.1/§8）。

## 3. 总体架构与关键决策

```
┌─ 消费方 App 进程 ──────────────────────────────────────────────────┐
│  环境引导层（bridge 载荷或 Kotlin）                                  │
│   - assets/git-bridge-tools/ 幂等物化 → filesDir                    │
│     （templates/ + cacert.pem + gitexec-manifest.json）             │
│   - 依 gitexec-manifest.json 建 helper 符号链接农场                 │
│     filesDir/gitexec/git-remote-https → <nativeLibraryDir>/…（D5）  │
│   - 注入 GIT_EXEC_PATH / GIT_TEMPLATE_DIR / GIT_CONFIG_GLOBAL /     │
│     GIT_SSL_CAINFO / SSL_CERT_FILE / PATH / HOME / TMPDIR（§7.1）   │
│        │ pty.spawn(<nativeLibraryDir>/libgit_cli.so, …)             │
│        ▼                                                            │
│  git 子进程（exec 型，独立生命周期；forkpty → setsid → TIOCSCTTY）    │
│   https 时：git 按 GIT_EXEC_PATH exec 农场里的 git-remote-https     │
│   （symlink → libgit_remote_curl.so，物理件在 nativeLibraryDir）     │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.1 关键决策记录（不可回归项）

| # | 决策 | 理由 | 反面（禁止） |
|---|---|---|---|
| **D1** | **exec 打包 `useLegacyPackaging=true`** | exec 要求物理落盘 nativeLibraryDir，不落盘则 `execve` ENOENT（C3） | `useLegacyPackaging=false`（pty dlopen 库的口径，与本仓相反） |
| **D2** | **zlib / libcurl / OpenSSL 全静态链入** | DT_NEEDED 只剩系统库，白名单门禁天然满足；产物单文件化，无运行期库查找 | 动态 .so 随包 + `LD_LIBRARY_PATH`（多文件多门禁、版本漂移；exec 子进程走默认 linker namespace，本就看不到 App 库目录） |
| **D3** | **缺项以 NO_* 配置关闭，不引入源码补丁**（`NO_TCLTK`/`NO_GETTEXT`/`NO_ICONV`/`NO_REGEX` + `NO_PERL`/`NO_PYTHON`） | fetch 不改源纪律；bionic 缺项用 git 自带 compat 补 | 第三方 fork / 源码补丁 |
| **D4** | **版本 = git 上游版本，独立 semver** | 与 node 系无 ABI 约束（同 python/uv/pnpm 口径） | 与 runtime/pty 配对（无必要） |
| **D5** | **https helper 以 `lib*.so` 随包 + `filesDir/gitexec` symlink 农场 + `GIT_EXEC_PATH` 指向农场** | C1：helper 物理件只能进 nativeLibraryDir（`lib*.so` 命名）；git 按 `<GIT_EXEC_PATH>/git-remote-<scheme>` 名字查找 helper → 农场提供原名 symlink，SELinux exec 检查解引用到**目标文件标签**放行（工作区 §4.3 命令农场同款）⬜ | 运行期下载 helper（C2 红线）；把 helper 拷进 filesDir（C1 封死）；不带 helper（https/clone 残废）；GIT_EXEC_PATH 直指 nativeLibraryDir（文件名不匹配，§5.2-d） |
| **D6** | **assets 只带纯数据**（templates / cacert.pem / gitexec-manifest.json），CA 经 env 注入不写死构建期路径 | filesDir 布局构建期不可知；物化复用 bridge payload 纪律 | curl `--with-ca-bundle` 写死路径（目标设备路径不可知） |
| **D7** | **GPLv2 对应源码随 Release 归档分发**（git/zlib/curl/openssl 源码 tarball ×4 + 构建脚本） | git 为 GPLv2（helper 同属 git 源码树），二进制分发必须附对应源码；"preferred form for modifications" = 钉版源码 + 脚本 | 仅给上游链接（义务履行存疑；措辞 M1 定稿 ⬜） |

## 4. 构建设计（M1 核心）

### 4.1 工具链与源钉选（四源表）

| 源 | 钉选与来源 | sha256 | 说明 |
|---|---|---|---|
| **git** | `github.com/git/git` releases `git-<ver>.tar.gz`；draft `2.51.0`，M1 钉选并回写 ⬜ | lock.builtFrom（M1） | 本体 → `libgit_cli.so` + helper 集（同一棵树同一次 make） |
| **zlib** | 官方源码包，版本 M1 钉选 ⬜ | lock.builtFrom.deps | `CHOST=aarch64-linux-android ./configure --static` ⬜ → `libz.a` |
| **OpenSSL** | 官方源码包，版本 M1 钉选 ⬜ | lock.builtFrom.deps | `./Configure android-arm64 no-shared no-tests` ⬜ → `libssl.a`/`libcrypto.a` |
| **curl** | 官方源码包，版本 M1 钉选 ⬜ | lock.builtFrom.deps | `./configure --host=aarch64-linux-android --disable-shared --enable-static --with-openssl --with-zlib --without-libpsl --without-brotli --without-zstd` ⬜ → `libcurl.a` |
| CA bundle | cURL 来源 `cacert.pem`，钉版 + sha256 | assets/manifest.json | 运行期 `GIT_SSL_CAINFO`/`SSL_CERT_FILE` 注入（D6） |
| NDK | 与 aosp-node-runtime 对齐（r28c 或更高）⬜ | lock.builtFrom.ndk | 一台 runner 一条 NDK 线 |

- **构建顺序（依赖方向）**：zlib → openssl → curl（依赖前两者）→ git；
- configure 路线：git 优先 `make configure && ./configure --host=aarch64-linux-android`
  （autoconf 进 runner 装机清单）；失败回退 `config.mak` 直写（Termux 同款）
  ⬜ M1 首轮试编拍板；
- runner 额外装机：autoconf、make/gcc（host 侧构建依赖）、curl/file/tar/xz（§9）。

### 4.2 交叉编译流程（scripts/build-git-cli-android.sh，M1 实现）

```
① env：TOOLCHAIN=<ndk>/toolchains/llvm/prebuilt/<host>；
   CC=aarch64-linux-android<api>-clang（API 默认 24）；AR/STRIP=llvm-*
② 依赖静态构建（产物全 .a，顺序 zlib → openssl → curl）：
   zlib:    CHOST=aarch64-linux-android ./configure --static ⬜
   openssl: ./Configure android-arm64 no-shared no-tests ⬜
   curl:    ./configure --host=… --disable-shared --enable-static
            --with-openssl --with-zlib --without-libpsl --without-brotli
            --without-zstd ⬜（缺库一律 --without-* 关闭，不引入新源）
③ git configure（make configure 生成 / config.mak 回退 ⬜）：
   NO_TCLTK / NO_GETTEXT / NO_ICONV / NO_REGEX（用自带 compat/regex）
   NO_PERL / NO_PYTHON（脚本钩子族不编）
   libcurl/OpenSSL/zlib 头文件与 .a 路径注入
   LDFLAGS="-Wl,-z,max-page-size=16384"
④ make -j$(nproc)：git 主可执行 + helper 集合——
   **helper 实际产物清单在此探明并回写 §5.2**（候选：git-remote-http
   及其 https/ftp/ftps 别名、git-http-fetch、git-http-push）⬜
⑤ llvm-strip --strip-unneeded → libgit_cli.so + libgit_remote_curl.so（等）
⑥ assets 收集：templates/（make install 模板产物或源码树 templates/，M1 定 ⬜）
   + cacert.pem + 生成 gitexec-manifest.json（helper 产物 → 农场清单）
⑦ BUILD-METADATA.txt / FETCH-METADATA.json（镜像 pty 归档形态）
```

要点与风险：

- **PT_INTERP**：bionic 动态可执行默认 interp = `/system/bin/linker64`，无需额外 flag；
  provision 门禁强制核验（§6）；
- **helper 与主二进制同一次 make 产出**，链接口径一致（静态依赖 + 16KB）→ 同过 exec 门禁；
- git 上游**无官方 Android/NDK 支持**（Termux 为社区维护先例）——交叉编译支持度全靠
  NO_*/config 参数注入回答，⬜ 是 M1-T3 试编的首要问题；失败退路见 R7/R8；
- **体积预估 ⬜**：本体 2–5MB + curl/openssl 静态增量 ≈5–8MB（工作区 §3.3 估），
  首产实测回填 lock；
- compat/regex 性能 ⬜（R3）；无 iconv 对中文路径影响 ⬜（R4，探针 P7 事实化）。

## 5. 制品形态与打包投放（AAR）

### 5.1 树

```
git-cli-<ver>.aar
├── jni/arm64-v8a/libgit_cli.so            # exec 型 PIE 主二进制（静态 zlib/curl/openssl，16KB 对齐）
├── jni/arm64-v8a/libgit_remote_curl.so    # remote helper（git-remote-http 同体；https 等经农场 symlink）
├── jni/arm64-v8a/libgit_http_fetch.so     # ⬜ M1 定：dumb-http helper 是否随包（§5.2）
├── jni/arm64-v8a/libgit_http_push.so      # ⬜ 同上（DAV push）
└── assets/git-bridge-tools/
    ├── templates/…                        # git 模板（hooks 仅为样例文件——运行期不可 exec，§7.2）
    ├── cacert.pem                         # CA bundle（钉版 + sha256）
    ├── gitexec-manifest.json              # 农场清单：命令名 → lib 文件名（引导层建 symlink 依据）
    └── manifest.json                      # 文件清单 + 逐文件 sha256 + 总 sha256
```

- 打包：**`useLegacyPackaging=true`**（D1）；模块只作 AAR 容器，无任何 Kotlin/Java 源；
- jniLibs 纪律：白名单 = `libgit_cli.so` + helper 集合（lock `matrix.jniLibsWhitelist`，
  M1 登记）；仍禁入 `libnode.so`；
- META-INF/git-cli.properties 增加 helper 清单与 deps 版本（M1-T5）。

### 5.2 helper 打包策略（本仓最关键设计：候选方案与取舍）

**难题陈述**：`git clone https://…` 不是 `libgit_cli.so` 单文件能闭环的——git 把 https/ftp
传输委托给**独立进程**的 remote helper：主进程按 `<GIT_EXEC_PATH>/git-remote-<scheme>`
的名字查找并 `exec`（`GIT_TRACE=1` 可见 `run_command: 'git-remote-https' …`）。⇒ helper
必须同时满足：①物理件可被 exec（C1 ⇒ 只能在 nativeLibraryDir 且名 `lib*.so`）；
②以 git 期望的名字可被查到（⇒ 需要一层名字映射）。**本地路径传输同理**：本地
clone/fetch/push 也经 exec-path 拉起 `git-upload-pack` / `git-receive-pack` 子进程 ⬜
（GIT_TRACE 可见 run_command 行）——农场不只服务 https helper，还服务本地 dashed 子进程。

| 候选 | 做法 | 判断 |
|---|---|---|
| **(a) helper 以 `lib*.so` 随包 + `filesDir/gitexec` 符号链接农场**（✅ 采纳，D5） | helper 物理件进 jniLibs 随包落盘 nativeLibraryDir；引导层物化 assets 后依 `gitexec-manifest.json` 在 `filesDir/gitexec/` 建原名 symlink（如 `git-remote-http`/`git-remote-https` → `<nativeLibraryDir>/libgit_remote_curl.so`）；`GIT_EXEC_PATH` 指向农场 | SELinux 对 symlink 的 exec 检查解引用到**目标文件标签**（nativeLibraryDir 域，放行）——与工作区 §4.3 `$HOME/bin` 命令农场同款；⬜ 真机验证（P5）；农场只是纯名字映射，不产生新代码 |
| (b) helper 拷贝物化进 filesDir | 物化时把 helper 复制为原名文件 | ❌ C1 封死：app_data_file 不可 exec |
| (c) 运行期下载 helper | 首启拉取缺失 helper | ❌ C2 红线 + Play 政策，违反工作区纪律 |
| (d) `GIT_EXEC_PATH` 直指 nativeLibraryDir | 免农场 | ❌ git 按名字 `git-remote-https` 查找，目录内文件名是 `lib*.so`，不匹配；且该目录应用不可写 |
| (e) isomorphic-git 等进程内替代 | 不带 helper | ❌ 工作区 §3.3 已否决（协议覆盖不全、无命令形态） |

**首版随包 helper 清单 ⬜（M1-T3 以 make 实际产物为准探明，本表为候选）**：

| 农场名（symlink） | 物理件（jniLibs 名） | 必要性 | 说明 |
|---|---|---|---|
| `git` | `libgit_cli.so` | ✅ | 农场含 `git → libgit_cli.so`（发行版 /usr/lib/git-core 同款惯例）；终端裸命令 `git` 由此可 PATH 直出，与 $HOME/bin 命令农场（工作区 §4.3）并存不冲突 |
| `git-upload-pack` / `git-receive-pack` / `git-upload-archive` | `libgit_cli.so`（按 argv[0] 分发） | ✅ | 本地传输子进程（同主二进制，argv[0] 名分发）；缺则本地 clone/fetch/push 失败 ⬜ |
| `git-remote-http` / `git-remote-https`（/`-ftp`/`-ftps` ⬜） | `libgit_remote_curl.so`（一体多别名） | ✅ **必随包** | remote-curl 单一二进制 + Makefile 别名（别名形态 symlink/hardlink 以 make 实产为准 ⬜）；https 传输核心；smart-http 全程在 helper 内完成 |
| `git-http-fetch` | `libgit_http_fetch.so` | ⬜ | 仅 dumb-http（老式静态仓库）用；裁剪则 dumb-http 如实登记不支持 |
| `git-http-push` | `libgit_http_push.so` | ⬜ | 仅 DAV push 用（现代 smart-http push 不经它）⬜ |
| `git-imap-send` 等其余 make 产物 | — | ❌ 默认裁剪 | 与传输主线无关；provision 白名单不含即不随包 |

- (a) 的前提与 ⬜ 验证点：①symlink exec 按目标标签放行（P5，R2）；②remote-curl 对
  argv[0] 无敏感性、别名共用一体 ⬜（P3/P4 对 http/https 两别名回归）；③make 产物清单
  与别名形态 ⬜（M1-T3 回写 §5.2/lock）；④16KB 设备农场链路 ⬜（P7）；
- 内建子命令（init/commit/add/log 等）在主二进制内（builtin），**不需要** farm 条目；
  farm 清单只登记"独立可执行"的产物（helper + dashed 子进程入口）。

### 5.3 provision 门禁扩展（M1 实现项）

- `--out` 投放主二进制 + helper 全集（依 lock 白名单，逐个过 exec 门禁）；
- `--check` 的 **jniLibs 兄弟文件白名单**从「仅 `libgit_cli.so`」扩展为
  「lock `matrix.jniLibsWhitelist`」（主二进制 + helper 集合）；白名单外 `.so` 仍拒绝；
  `libnode.so` 禁入不变；
- **gitexec-manifest.json 一致性校验**：manifest 引用的每个 lib 必须在 jniLibs 白名单内
  且过门禁；反向无孤儿（白名单内每个 helper 都有农场条目或有明确裁剪理由）；
- assets 投放（`--assets`，同 python-cli 口径）：templates/CA/农场清单进 assets 并生成/
  校验 manifest.json（逐文件 sha256；assets 内不得出现 `.so`/可执行位文件）。

## 6. exec 型门禁 profile

| 门禁 | 判据 | 与 pty（dlopen 库）门禁的差异 |
|---|---|---|
| ELF 形态 | `ET_DYN`（PIE） | 同 |
| 解释器 | **PT_INTERP 恰 1 个且 = `/system/bin/linker64`** | **相反**（pty 要求 PT_INTERP=0） |
| 依赖 | **DT_NEEDED 白名单**（系统库 + lock 登记） | pty 是"必须含 libnode.so" |
| NAPI | 无门禁 | pty 有"napi_* 未定义引用"门禁 |
| 页对齐 | 16KB（`-Wl,-z,max-page-size=16384`） | 同 |
| 出处 | sha256 / size / 源版本 / NDK / flags | 同 |
| **命名** | `lib*.so` 前缀；helper 用 `libgit_<名>.so` 映射名 | 新增（helper 不可能用原名，§5.2） |

- **已实现（M0）**：provision 退出码 0/2/1；draft 只记录不比对（sha/size）；
- **M1 新增**：① **helper 全集过同一 exec 门禁**——helper 也是完整可执行（PIE +
  INTERP=linker64），不是 dlopen 库，profile 与主二进制相同；② jniLibs 白名单扩展
  （§5.3）；③ gitexec-manifest 一致性校验；④ assets/manifest 校验（纯数据纪律）。

## 7. 运行期契约（消费方 / 环境引导层）

### 7.1 env 注入表

| 环境变量 | 值 | 说明 |
|---|---|---|
| `GIT_EXEC_PATH` | `<filesDir>/gitexec` | **symlink 农场**（引导层依 gitexec-manifest.json 创建/重建，幂等）；git 在此查找 `git-remote-*`、`git-upload-pack` 等 helper/dashed 子进程 |
| `GIT_TEMPLATE_DIR` | `<filesDir>/git-bridge-tools/templates` | 物化后的模板目录（构建期默认路径在设备上不存在，必须显式注入） |
| `GIT_CONFIG_GLOBAL` | `<HOME>/.gitconfig` | 用户配置落 filesDir（可写） |
| `GIT_CONFIG_NOSYSTEM` | `1`（建议）⬜ | Android `/etc/gitconfig` 不可控，读盘行为与之隔离 |
| `GIT_SSL_CAINFO` | `<filesDir>/git-bridge-tools/cacert.pem` | **主注入点**：git 显式传给 libcurl（CURLOPT_CAINFO） |
| `SSL_CERT_FILE` | 同上 | libcurl 的 env 钩子（≥7.84）⬜ 兜底 |
| `PATH` | `<nativeLibraryDir>:<filesDir>/gitexec:$HOME/bin:/system/bin` | 命令直出 + dashed 兜底；裸命令 `git` 靠农场/命令农场条目（§5.2） |
| `HOME` / `TMPDIR` | filesDir 子目录 | 对象库、锁文件与临时文件 |
| `GIT_PAGER`（建议） | `cat` | 无 pager，防 `log`/`diff` 交互挂起 ⬜ |

- 物化机制：复用 bridge payload 纪律（marker 幂等、失败结构化上报、版本升级清残留）；
  **农场在物化后创建/重建**（先清 `gitexec/` 再按 manifest 建全量 symlink，防旧版残留）。

### 7.2 已知限制（消费方文档必须写明）

- **ssh 远程不可用**：`git@…` / `ssh://` 需另带 ssh 二进制（openssh/dropbear，二期）；
- **perl/tcl 依赖子命令不可用**：send-email / svn / gitk / git-gui / cvsserver / mergetool
  等（NO_PERL/NO_TCLTK 不编 + GIT_EXEC_PATH 农场无脚本）；`git p4`（python）同；
- **仓库钩子不可执行**：钩子脚本落 filesDir（SELinux C1 不可 exec），git 以
  `access(X_OK)` 探测失败 → **视为无钩子（跳过）**⬜（确切警告行为 P2 记录）；
  CI 类自动化不能依赖 git hooks；
- **无 iconv（NO_ICONV）**：路径/提交信息按原字节透传（UTF-8 仓库正常）；非 UTF-8
  编码仓库的转码能力缺失，中文路径行为以 P7 记录为准 ⬜；
- **compat/regex（NO_REGEX）**：功能齐（git 自带），性能与系统 regex 有差 ⬜；
- dumb-http（git-http-fetch）/ DAV push（git-http-push）是否可用随 §5.2 裁剪决定 ⬜；
- 无 gettext：输出仅英文（C locale）；
- 服务端角色（`git daemon`、托管型 receive-pack 服务）不在范围。

## 8. 唯一事实源：`git-cli.lock.json`

镜像 pty/node-cli/python-cli 纪律：版本 + 大小 + sha256 + 门禁 + 出处，二进制不入库。
当前唯一 release 为 **draft**（`2.51.0`；size=0、sha256 空）——draft 不伪造哈希，首个真实
CI 构建后回写并以实际钉住的 git 版本为准。M1 扩展：

- `releases[].builtFrom.deps` 从自由文本升级为**版本表**：
  `{zlib:{version,sha256}, curl:{…}, openssl:{…}}`（M1-T1 回写）；
- `matrix.allowedNeeded` 维持系统库白名单；静态链入后实际 NEEDED ⊆ libc/libm/libdl/liblog，
  `libz.so` 条目为防御性允许（M1 复核 ⬜）；
- `matrix` 新增 **`jniLibsWhitelist`**（主二进制 + helper 集合，§5.3/§6）与
  gitexec-manifest 语义说明；
- helper 产物在 `releases[].builtFrom` 登记（helper 清单 + 逐个 sha256，M1-T3/T5）。

## 9. CI 设计（真实流水线，M1 替换 scaffold CI）

现 workflow（`.github/workflows/build-git-cli-android.yml`）仅为**配置期门禁**
（Gradle 配置 + provision 语法/退出码自检），M1 替换：

- runner：`ubuntu-24.04`（4 vCPU）；装机：NDK（与 runtime 对齐线 ⬜）、JDK 21、Node 20、
  **autoconf**（git `make configure` 需要）⬜、make/gcc、curl/file/tar/xz、ccache；
- 步骤：resolve version（tag `v<gitver>` push 或 dispatch）→ fetch 四源 + cacert
  （各 sha256 钉选）→ 依赖静态构建（zlib → openssl → curl，产物全 `.a`）→
  git configure（§4.2 ③）→ make → **helper 清单探明**（§4.2 ④）→ strip（llvm-strip）→
  provision（主 + helper 全门禁 + jniLibs 白名单 + assets）→ 归档
  `git-cli-v<ver>-android-arm64-v8a.tar.gz`（lib*.so 集 + assets + BUILD/FETCH-METADATA +
  LICENSES + **源码 tarball ×4 与构建脚本——GPLv2 对应源码义务，D7**）+ `.sha256` →
  GitHub Release（tag 钉 commit）→ artifact 上传 → lock 人工回写（M4 自动化评估）；
- 缓存：ccache + zlib/openssl/curl 构建缓存（整链首轮 ⬜ 15–30min 量级，实测定策略）。

### 10.1 发布模式（GitHub Release 先行、Maven Central 随后）

沿用 aosp-node-pty 的两段式发布：

1. **先行：GitHub Release（M1-T6，tag `v<gitver>` 推送触发）**——归档
   `git-cli-v<ver>-android-arm64-v8a.tar.gz`（libgit_cli.so + helper 集合 + templates/CA
   assets + 元数据 + LICENSES）与 `.sha256`，lock 回写 `status=released`；**归档必须同时
   分发构建所用源码 tarball（git/zlib/curl/openssl 四源）与构建脚本**（git 为 GPLv2，
   对应源码义务以此满足，D7）；
2. **随后：Maven Central（M3）**——执行口径按工作区
   [`docs/发布到maven-central.md`](../../docs/发布到maven-central.md) runbook（§2 一次性凭据 →
   §4 发布前检查 → §5 上传 → §6 核验回填 `mavenCentral.published=true`）；本仓
   `publish.gradle.kts` 已内置该管线（RELEASE=false 默认，POM SCM url 补丁指向本仓）。

- 与 pty 的差异：版本源 `CLI_VERSION`（= git 上游版本，独立 semver，无 NODE_ 前缀约束、
  无配对顺序要求）；helper/assets（templates/CA/农场清单）随 AAR 一同发布，manifest 校验
  纳入 Maven 阶段发布前检查（runbook §10 已登记本线复用，⬜ 首次实走后回填）；
  **GPL 措辞（AAR/NOTICES/Maven sources jar 与对应源码的表述）M1-T6 前定稿** ⬜（R5）。
